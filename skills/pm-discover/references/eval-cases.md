# pm-discover eval cases

Behavioral prompt fixtures for `pm-discover`. The fixture project is `tests/fixtures/flat-root/context/`
(project `recipe-fridge`: greenfield `prd.md` with `status: draft`, no `shape-notes.md`, no `prd-review-*.md`,
a `roadmap.md`, no `foundation/tech-stack.md`). Cases that need other files say which to add or remove in a
scratch copy. To try one by hand, copy the fixture into a scratch git repo and run Claude Code with the plugin
loaded (see the README, "Local testing"). Every case also implies the guardrails in `SKILL.md`: one human gate
between steps, stage re-derived from disk after every hand-back, nothing written by this skill except the
confirmed moves.

| ID | Given | Invoke | Expected |
|---|---|---|---|
| DS-01 | An empty repository: no `context/` folder, no `.sdd.yml` anywhere. | `/pm-discover` | Root discovery finds nothing → stage `uninitialized`. The skill says in plain words that there is no notes folder yet and offers `/pm-init` and nothing else ("Set it up? Yes (Recommended) / Not now"); it does not ask for the idea, the project or the audience and does not mention shaping, the PRD or the roadmap. On yes it invokes `/pm-init`, on return discovers the root again and re-derives (now `unshaped`), then stops at the next gate. Fail if it invokes any other skill, starts shaping, or runs `/pm-init` without a yes. |
| DS-02 | Root exists; `foundation/recipe-fridge/research/2026-10-12-fridge-habits.md` exists with a `## Seed for shaping` section; no `shape-notes.md` and no `prd.md` in that folder. | `/pm-discover` (confirm the project when asked, answer yes at the gate) | Stage `unshaped`, research found. Before invoking, the operator is told which project name to confirm in `/pm-shape` ("Recipe Fridge", in words, no folder talk in plain mode). The Skill tool is called for `pm-shape` with the argument `@<path of the research file>` (the file, not a pasted summary). No `/pm-frame` offer, because research gives the problem. Fail if `/pm-shape` is invoked without the path, without a yes, or without the project-name hint. |
| DS-03 | `foundation/recipe-fridge/shape-notes.md` exists with frontmatter `checkpoint: { current_phase: 4, phases_completed: [1, 2, 3], … }` and no `prd.md`. The operator says "it feels done, let's write the PRD". | `/pm-discover` | Stage `shaping` (phase 4 is below 8). The next step is `/pm-shape`, which resumes from its checkpoint; the skill invokes it on yes with no idea text. It explains that the closing cross-check has not finished and does **not** route to `/pm-prd`, even on the operator's request. With `current_phase: 8` the same files give stage `shaped` and the next step `/pm-prd @<shape-notes path>`. Fail if `/pm-prd` is offered or invoked while `current_phase` is below 8, or if the stage is read from the conversation instead of the file. |
| DS-04 | DS-02 was run; in `/pm-shape` the operator picked **Rename** and typed a different name, so `shape-notes.md` now sits in `foundation/fridge-planner/` while the research is still in `foundation/recipe-fridge/research/`. | continue after `/pm-shape` returns | The skill compares the new `shape-notes.md` location with the research folder and finds different slugs. It asks, in plain words, whether to move the research next to the product and recommends yes. It does not move anything before the answer. On yes it runs `git mv foundation/recipe-fridge/research foundation/fridge-planner/research` under `$CONTEXT_ROOT`, says the move is staged not committed, leaves the old folder in place. On "leave it" or "not sure" nothing moves and it says where the research stays. Destination `research/` already exists → lists the files that would move and never overwrites. In plain mode the command is not shown. Fail if the research moves without a yes, silently, or by overwriting a file. |
| DS-05 | The fixture as it stands: `prd.md` `status: draft`, no `prd-review-*.md`, no `shape-notes.md`. `pm-prd-review` is available. | `/pm-discover recipe-fridge` | The project is resolved without asking. Stage `specified` (a `prd.md` without `shape-notes.md` does not send the project back to shaping; row 5 wins over a present `roadmap.md`, and the skill says a build plan already exists so the review is a check after the fact). Recommendation: `/pm-prd-review`, first option "Yes, review it (Recommended)", plus "Skip the review this time" and "Not sure". On yes it invokes `/pm-prd-review`; on return it re-derives from disk. If `pm-prd-review` is not available in the session it says so plainly, skips with a note and does not claim a review happened. Fail if it recommends `/pm-shape`, `/pm-prd` or `/pm-roadmap` first, or invokes the review without a yes. |
| DS-06 | Only `sdd-pm-skills` is installed (no other plugin of any kind); the fixture root and project as in DS-05. | `/pm-discover recipe-fridge` | The run never mentions installing, adding or enabling another plugin or marketplace and prints no install block or dependency check: it goes straight to root and project resolution, derives the stage from disk (as in DS-05) and offers the single next step, naming only `pm-*` commands. Fail if it asks the operator to install anything, STOPs before deriving a stage for lack of another plugin, or offers a step that is neither a `pm-*` command nor a developer's step in generic words. |
| DS-07 | The fixture with `prd-review-2026-10-18.md` with frontmatter `verdict: APPROVED` added next to `prd.md` (so the PRD counts as reviewed) and `roadmap.md` removed; `foundation/tech-stack.md` absent at the root (`context_type: greenfield`). | `/pm-discover recipe-fridge` | Stage `stack-pending`. In plain mode it explains that one technical decision is open and that choosing the technology is a step for a developer, and offers: 1. hand this to a developer (Recommended), 2. skip it and make the build plan now, 3. not sure. It does **not** invoke `/pm-roadmap` until the PM picks 2. On 1 it prints a short note for the developer (choose the tech stack in their development workflow, recorded in `foundation/tech-stack.md`; for a brownfield PRD assess the existing stack and run a health check, recorded in `foundation/stack-assessment.md`), says to re-run `/pm-discover` afterwards, and stops. On 2 it warns once that the plan may need rework, then offers `/pm-roadmap` as a separate gate, and the next run asks about the stack again. With `foundation/tech-stack.md` present the stage is `reviewed` and the next step is `/pm-roadmap`. Fail if `/pm-roadmap` or a stack skill is invoked without the PM's explicit choice, or the gate is skipped by default. |
| DS-08 | The fixture with `prd-review-2026-10-18.md` (`verdict: APPROVED`) **and** a later `prd-review-2026-10-19.md` with frontmatter `verdict: REJECTED` next to `prd.md` (`status: draft`); `roadmap.md` removed; `pm-prd-review` is available. | `/pm-discover recipe-fridge` | The latest report (by date, then `-N` suffix) is the 19th, so its verdict decides: the PRD is **not reviewed** and the stage stays `specified` (never `stack-pending`). In plain words the skill says the last review found things that must be settled and recommends picking it back up: "Yes, resume it (Recommended) / Start a fresh review / Skip the review this time / Not sure". On yes it invokes `/pm-prd-review` with the path of the 19th report (resume mode), not a fresh review. "Skip" is for this run only and the skill says the last review was not approved. With the 19th report set to `verdict: APPROVED`, or with `prd.md` `status: reviewed`, the stage is `stack-pending`. Fail if the stage is `stack-pending` or `reviewed` because a report file exists, if an older APPROVED report overrides a later REJECTED one, or if `/pm-prd-review` is invoked without a yes. |
| DS-09 | An empty root with no project yet (or the fixture); the operator says "build a recipe-sharing feature" (solution-shaped: no problem, user or pain stated); `/pm-frame` is available. | `/pm-discover "build a recipe-sharing feature"`, answer 1 to the framing check | The skill snapshots `foundation/*/frame-*.md`, invokes `/pm-frame` with the idea verbatim, then re-derives. It finds the new `foundation/<slug>/frame-<date>-<topic>.md` (the newest) and on the go-ahead invokes `/pm-shape @<that frame path>` — **not** `/pm-shape <idea verbatim>` - so the reframed problem is the seed. Before invoking it tells the operator which project name to confirm (the frame's folder name in words, e.g. "Recipe Sharing"; in plain mode without folder talk). If the operator then picks a different name and `shape-notes.md` lands in `foundation/<slugB>/` while the frame file sits in `foundation/<slugA>/`, the skill asks, in plain words, whether to move the framing next to the product (recommends yes) and does nothing before the answer; on yes it runs `git mv foundation/<slugA>/frame-<date>-<topic>.md foundation/<slugB>/frame-<date>-<topic>.md` (both slugs checked against `^[a-z0-9]+(-[a-z0-9]+)*$` first, else STOP and explain), says it is staged not committed, never overwrites a file in the target, offers plain `mv` when the file is untracked, and does not show the command in plain mode. If `/pm-frame` wrote no brief, it says so in one line and falls back to `/pm-shape <idea verbatim>`. Fail if the idea text rather than the frame path is handed to shape, if the project name is not announced, or if the frame file moves without a yes. |
