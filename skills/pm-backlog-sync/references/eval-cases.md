# pm-backlog-sync eval cases

Behavioral prompt fixtures for `pm-backlog-sync`. The fixture project is `tests/fixtures/flat-root/context/` (project `recipe-fridge`; its
roadmap `## Backlog Handoff` has 7 rows: F-01 `auth-scaffold`, S-01 `fridge-inventory`, S-02 `recipe-match`, S-03 `save-favorites`,
S-04 `shopping-list`, S-05 `meal-plan`, S-06 `share-recipe`; the first four are `done`). The shared fixture is **not changed**: where a case
needs a different state the Given describes the variant to apply to a scratch copy. The fixture root has no tracker tool, so BS-06 is what a
manual run on it hits; BS-01 to BS-05 assume the host also exposes a Jira tool set (names containing `jira`: get issue, create issue,
update issue, create link, transition, search). The decision table is covered by `scripts/validate-pm-evals.sh`; these cases cover what the
skill says and writes. Every case also implies the guardrails in `SKILL.md` (never deletes, preview then `Apply`, keys only in
`tracker-map.md`, no invented content).

| ID | Given | Invoke | Expected |
|---|---|---|---|
| BS-01 | The fixture as is; a Jira tool set is connected; `pm-config.yml` and `tracker-map.md` do not exist; the PM answers Jira, project key `KAN`, no epic. | "sync the backlog to Jira" | Contract check passes for roadmap and PRD. The skill lists the Jira tools it found and asks for confirmation before any write. It previews **7 creates** (S-01..S-06 as Story, F-01 as Task; titles verbatim from the Backlog Handoff table; each labelled `sdd:<change-id>`), the dependency links between roadmap IDs (S-01 blocked by F-01, S-02 by S-01, S-03 by S-02, S-04 by S-02, S-05 by S-03, S-06 by S-04; the text `ingredient unit convention agreed` is listed as not linked), and the totals. It offers exactly `Apply` / `Export file instead` / `Cancel`. **Nothing is written before `Apply`**: no issue, no `tracker-map.md`; `pm-config.yml` keys `tracker: jira` and `tracker_project: KAN` are written only after the PM confirmed them. After `Apply`: 7 issues created sequentially, one map row appended after each, links created, then a separate offer to move the four `done` items (F-01, S-01, S-02, S-03) to Done. Each description holds the Outcome, PRD refs, the Given/When/Then of the named user story (S-02: US-01), `Change ID: recipe-match` and the roadmap path; F-01 (PRD refs `Access Control`) says no user story is linked. |
| BS-02 | The state after BS-01 completed (7 rows in `tracker-map.md`, all issues present, nothing changed in the roadmap; the four done items already moved to Done). | "sync the backlog again" | Every row is `skip` (the title equals `Synced title`, the recomputed hash equals `Synced hash`); no link is missing. The skill says everything is already in the tracker and nothing changed, offers no write, and writes nothing (the map's `updated` is not touched). A recomputed hash is produced by running the command, not by eye. |
| BS-03 | The fixture, empty map, Jira connected; the PM chose `Apply`; the 4th create fails (the tracker returns an error). | "sync the backlog to Jira" (then again after the error is fixed) | Creates 1 to 3 succeed and each map row is appended immediately, so the map holds **3 rows** when the run stops. The skill stops at the first error (no 5th create, no links), reports the failing item, the error text, 3 created and 4 not attempted. The re-run loads the map, marks 3 rows `skip` (their issues are fetched), and previews only the **remaining 4 creates** (plus the links not yet present); it does not create duplicates of the first three. |
| BS-04 | The state after BS-01. In a scratch copy the roadmap's S-03 Change ID `save-favorites` is renamed to `favorite-recipes` (heading, At a glance, Backlog Handoff). | "sync the backlog" | `save-favorites` is in the map but not in the roadmap → `orphan`: its row moves to `## Orphans` and its issue is **not touched** (reported as kept). `favorite-recipes` has no map row → `create`; because an orphan has the same Roadmap ID (S-03) the preview adds "relink offered: reuse `<key>`". If the PM accepts, the action becomes an `update` of that issue (title/description, new label `sdd:favorite-recipes`), and the row returns to `## Issues` under the new Change ID; if declined, a new issue is created and the old issue stays. Nothing is deleted or closed either way. |
| BS-05 | The state after BS-01, then the issue mapped to S-04 (`shopping-list`) is deleted in Jira. | "sync the backlog" | Fetching the mapped key returns "not found" → `relink-ask` for S-04 (all other rows `skip`). The skill asks: link an existing issue, create a new one and replace the key, or leave unsynced. It **never recreates automatically**. A fetch that fails for another reason (permission, network) is not treated as deleted: the run stops and reports the failure. Option 3 leaves the map row unchanged and the report says S-04 is still unsynced. |
| BS-06 | The fixture as is; the host exposes no tool whose name contains `jira` or `linear`. | "push the roadmap to Jira" | The skill says it found no tracker connection, runs no write, and goes to the export fallback: asks Jira or Linear only to pick the format. For Jira it writes `exports/backlog-<date>.csv` with the header exactly `Summary,Issue Type,Description,Labels`, 7 data rows (RFC 4180 quoting; descriptions with commas and newlines survive a CSV reader), labels `sdd:<change-id>`. The first line of the result says **no issues were created**; `tracker-map.md` is not written; the four done items are listed as "mark these Done after import"; it explains how to import and warns not to import the file and sync later. For Linear the output is `exports/backlog-<date>.md`, a checklist with `- [x]` for the done items. |
